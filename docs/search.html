Two-Stage Selective-Load Search Engine

How EPSE executes low-latency similarity queries on massive datasets without exceeding constrained RAM budgets.

The Two-Stage Search Architecture

Direct linear search over 10 million protein embeddings (each 480 floats = 19.2 GB) requires massive RAM and computational overhead. EPSE prunes the search space through a two-stage retrieval strategy:

Stage 1: Centroid Ranking

  • The query sequence is passed through the ESM-2 embedder on CPU, generating a unit-normalized vector q in R^480.
  • The query vector is evaluated against the cluster centroids C in R^(k x 480) via matrix multiplication: scores = C . q.
  • The top M cluster IDs with the highest inner products are selected (typically M = 2 to 5).

Stage 2: Selective Disk Loading & Candidate Ranking

  • Using the inverted cluster index (cluster_index.json), EPSE resolves the exact list of protein IDs belonging to the top M clusters.
  • Only those candidate embeddings are retrieved from embeddings.bin via zero-copy memory mapping (np.memmap), ensuring fast random access without reading non-matching clusters into RAM.
  • Fine-grained cosine similarities are computed across the candidate subset, producing the final ranked top-K results.

Constant-Time O(1) Binary Storage (epse.storage)

Every embedding in embeddings.bin is written with a fixed byte footprint:

Record Layout:
[ 4 bytes: uint32 protein_id ] + [ 480 * 4 bytes: float32 embedding coordinates ] = 1924 bytes

To read the vector for protein i (1-indexed), the storage manager indexes directly via virtual memory mapping or seeks to byte offset (i - 1) * 1924. Non-selected clusters remain unpaged on disk, ensuring memory usage depends strictly on the cluster size rather than total database scale.
